# B-03D — Diseño previo de confirmación financiera y concesión

**Estado:** borrador técnico para revisión del promotor, 11 de noviembre de 2026. Ninguna propuesta nueva de este documento constituye una decisión aprobada. Base inspeccionada: `ca59f993d8c6ba34926cbe4d68907b17dbc1d9a2`. No se implementó integración con Stripe ni se habilitaron pagos.

## Frontera existente

`Order`, `PaymentAttempt`, `CheckoutRequest`, `PaymentProviderEvent` y `DeliveryEntitlement` ya expresan la compra de un producto, la sesión, la evidencia recibida y el derecho. B-03C verifica la firma y conserva el evento, pero `VERIFIED` no confirma pago. Las funciones R01 de `0012` impiden `PAID` y `SUCCEEDED`; `0014` impide `APPLIED`; `0006` exige orden pagada e intento exitoso antes de insertar el derecho. El flujo público de Checkout y el receptor webhook permanecen deshabilitados.

## 1. Contrato propuesto de `paid_at` para captura automática

**Fuente:** `created` del evento Stripe `payment_intent.succeeded` del PaymentIntent enlazado a la Checkout Session, convertido desde segundos Unix a UTC. Se conserva también el ID de ese evento y el código de fuente `stripe_payment_intent_succeeded_event_created`. Este timestamp es la hora de creación del evento de éxito de Stripe, con resolución de un segundo; se adopta como marca operativa del éxito, sin afirmar precisión subsegundo ni sustituirlo por la hora de recepción local. La elección de esta fuente aún requiere aprobación del promotor.

El trabajador obtiene el evento por ID o busca de forma paginada eventos `payment_intent.succeeded` de la cuenta y entorno correctos. La API de eventos solo ofrece los últimos 30 días. Una notificación B-03C de Session no sustituye el evento de éxito del PaymentIntent. La consulta de Session, PaymentIntent y todas las líneas se realiza de nuevo con el proveedor; nunca se decide a partir del cuerpo webhook almacenado.

Antes de aceptar la marca deben concordar: `event.type`, `event.data.object.id = PaymentIntent.id`, cuenta y `livemode`; Session vinculada a `CheckoutRequest` e intento; `mode=payment`, `payment_status=paid`, PaymentIntent `status=succeeded` y `capture_method=automatic`; importe total y `amount_received` iguales al snapshot en MXN; una sola línea, cantidad 1, Price ID y Product ID fotografiados, sin descuentos o impuestos no previstos. El evento debe ser temporalmente coherente con la creación de la Session y del PaymentIntent; fechas futuras o varios eventos de éxito incompatibles se tratan como contradicción. Una señal posterior de reembolso o disputa conocida no se interpreta como pago nuevo concedible.

**Si falta el evento de éxito, la paginación está incompleta, Stripe no responde, o la marca es contradictoria:** no se asigna `paid_at`, no se cambia `Order` a `PAID`, no se cambia el intento a `SUCCEEDED` y no se crea derecho. Se conserva la observación de pago y la causa saneada para conciliación; se reintenta dentro del plazo de consulta. Al expirar los 30 días sin fuente verificable, se requiere revisión manual documentada. No se usa `Session.created`, `PaymentIntent.created`, `Charge.created`, `now()` ni la llegada del webhook como sustituto silencioso.

Referencias Stripe: [Event y `created`](https://docs.stripe.com/api/events/object), [consulta de eventos y límite de 30 días](https://docs.stripe.com/api/events/list), [Session](https://docs.stripe.com/api/checkout/sessions/object), [PaymentIntent](https://docs.stripe.com/api/payment_intents/object), [líneas completas](https://docs.stripe.com/api/checkout/sessions/line_items). La documentación de Stripe llama a `Event.created` hora de creación del evento; usarlo como marca operativa del éxito es una **propuesta de contrato del proyecto**, no una garantía de precisión que Stripe documente.

## 2. Roles y ejecución restringida en PostgreSQL

| Rol | Login y permisos propuestos |
| --- | --- |
| `mp_migrator` | Credencial de despliegue aislada; aplica migraciones y posee las tablas y triggers. Nunca se usa en el proceso web. |
| `mp_finance_owner` | `NOLOGIN`, sin superusuario ni `BYPASSRLS`; propietario solo de la función financiera `SECURITY DEFINER`, con DML concedido sobre las tablas estrictamente necesarias. No posee tablas ni puede deshabilitar triggers. Solo migraciones controladas pueden administrar este rol. |
| `mp_web_test` / `mp_web_live` | Usuarios del proceso web, segregados por base/entorno; DML ordinario indispensable para órdenes, intentos y recepción B-03C, sujeto a triggers. Sin membresía financiera, `EXECUTE` financiero, propiedad de tablas, `TRIGGER`, `CREATE` en esquemas de confianza ni capacidad de alterar/deshabilitar triggers. |
| `mp_finance_test` / `mp_finance_live` | Login del trabajador conciliador, separado del web y por entorno. `SELECT` mínimo de correlación y `EXECUTE` solo de funciones de registrar verificación y confirmar. Sin DML directo sobre orden, intento, derecho, auditoría o evento; sin membresía de `mp_finance_owner` o `mp_migrator`. |
| `mp_readonly` | Soporte/observabilidad de datos saneados, sin DML ni `EXECUTE` financiero. |

La configuración de despliegue deberá demostrar que el usuario web no es propietario de las tablas y que ningún rol de aplicación puede cambiar de rol a `mp_finance_owner` o `mp_finance_*`. Las credenciales TEST y LIVE nunca se intercambian. PostgreSQL CI necesitará conexiones separadas para migrador, web y conciliador; probar solo con el superusuario del contenedor no acredita esta frontera.

La función financiera se instala en un esquema confiable, con nombre cualificado, `SECURITY DEFINER`, `search_path` fijado a `pg_catalog, public, pg_temp` y los objetos nuevos referidos por esquema. `public` permanece en la ruta porque los triggers heredados R01 usan nombres de tabla sin cualificar; se revoca `CREATE` sobre ese esquema a `PUBLIC` y el usuario web no puede crear allí. Se revoca `EXECUTE` de `PUBLIC` antes de uso; se concede solo al rol financiero del entorno. Valida argumentos de tipo limitado e identidades persistidas, bloquea filas, exige una verificación autoritativa durable y realiza el cambio completo. No recibe un booleano `paid`, una orden pública como credencial ni JSON libre. Los triggers reconocen la ejecución por **identidad efectiva del dueño de la función y `session_user` del trabajador autorizado**, junto con precondiciones de filas y evidencia, nunca por `current_setting()` o un marcador que el usuario SQL pueda fijar. El trabajador no tiene DML directo: el par de identidades tampoco es una autorización suficiente por sí solo.

El proceso conciliador es parte de la base de confianza: una credencial de ese proceso comprometida podría presentar hechos falsos a la función. La base no verifica criptográficamente una respuesta HTTPS de la API de Stripe. Se limitan la credencial Stripe, el rol SQL, el entorno y los datos aceptados; se auditan sus operaciones. Dueño de base y superusuario quedan fuera de la garantía contra manipulación ordinaria.

## 3. Evidencia durable, transacción y recuperación

Se propone una entidad mínima `FinancialVerification` (nombre sujeto a implementación) que conserve **solo hechos normalizados**: cuenta, entorno, orden, intento, Session ID, PaymentIntent ID, evento de éxito y fuente temporal, `paid_at` propuesto, importes/moneda, Price/Product ID, cantidad, `checked_at`, estado (`PENDING_DELIVERY`, `APPLIED`, `REVIEW`) y códigos saneados. Su inserción está restringida al trabajador; la identidad y los hechos verificados son inmutables. No conserva cuerpos completos, correo, tarjetas, secretos ni respuestas JSON. Una clave de operación estable identifica la misma conciliación; unicidad sobre cuenta/entorno/Session/PaymentIntent y sobre la concesión aplicada impide duplicación. El evento B-03C relacionado se referencia cuando existe; una conciliación sin webhook identifica explícitamente su origen.

La consulta a Stripe y la comprobación del almacenamiento ocurren **fuera** de la transacción de confirmación. El trabajador registra primero la verificación durable. Si el archivo no existe, el digest o tamaño difiere, o la versión no puede recuperarse, no llama a la operación de concesión. El registro queda `PENDING_DELIVERY` ante error temporal o `REVIEW` ante pérdida/inconsistencia; orden e intento conservan sus estados no pagados internos, aunque Stripe ya haya cobrado. Se alerta a operación y se bloquean nuevos intentos/sesiones para esa orden mientras exista una verificación de pago externa. El sistema no informa al comprador que la entrega está lista ni genera otro cargo.

Una recuperación consulta nuevamente Stripe y la versión privada, reutiliza la misma verificación o registra una revisión vinculada sin cambiar `paid_at`. Una vez disponible la versión exacta, invoca la concesión. Si vence el derecho antes de resolver la entrega, se escala soporte; no se reinician unilateralmente las 336 horas. Si el archivo se perdió definitivamente, el tratamiento de reembolso o alternativa requiere política aprobada y actuación operativa; B-03D no inventa una versión sustituta.

La operación restringida bloquea siempre **orden → intento → CheckoutRequest → verificación → evento relacionado**, y comprueba de nuevo contradicciones, estados, cuenta, entorno, importes, identidad de archivo y ausencia de otro derecho. En una sola transacción asigna PaymentIntent, `SUCCEEDED`, `PAID` y `paid_at`; inserta el único `DeliveryEntitlement` con `expires_at = paid_at + 336 horas`; inserta auditoría correlacionada de intento, orden y concesión; y marca verificación y evento causal como aplicados. La unicidad de derecho por orden e intento sigue vigente. Un fallo en cualquier paso revierte todos los cambios de esa transacción. La verificación durable anterior permite reintentar sin crear otro cargo.

Si la respuesta local se pierde **después** del commit, el reintento bloquea las mismas filas y devuelve el derecho existente únicamente cuando todos sus identificadores, tiempo e identidad de archivo coinciden. Una diferencia entra en revisión; no se hace una segunda transición ni concesión. Las notificaciones tardías de fallo/expiración no retroceden `PAID`.

## 4. Conciliación autoritativa sin webhook

Un trabajo interno programado o una operación de soporte auditada selecciona `CheckoutRequest` vinculadas o inciertas que superaron su plazo de respuesta y no tienen derecho. Usa la cuenta y entorno del intento, recupera la Session por ID; para una solicitud `UNCERTAIN` sin ID, primero recupera la operación mediante la misma clave idempotente o mecanismo de recuperación que B-03B deba completar. **No crea una nueva Session.** Recupera PaymentIntent y todas las líneas, y localiza el evento `payment_intent.succeeded` dentro de la ventana de 30 días. Ejecuta exactamente el mismo validador y la misma función financiera que el camino iniciado por webhook. El origen se registra como `provider_poll`, sin fabricar una fila B-03C que aparente un webhook firmado.

Los reintentos del trabajo tienen clave estable por cuenta, entorno, Session y PaymentIntent; la unicidad local y el bloqueo PostgreSQL resuelven carreras con un webhook posterior. La idempotencia de la consulta no equivale a autorización para conceder: cada intento revalida los datos actuales y las contradicciones antes de aplicar. Si la Session sigue abierta, el PaymentIntent no ha triunfado, faltan líneas o falta el evento de éxito, permanece pendiente. Más allá de 30 días sin evento accesible, la vía automática se detiene y solicita conciliación manual. El alcance de la recuperación de `UNCERTAIN` sin Session ID es una dependencia no resuelta de B-03B.

## 5. Evolución selectiva de triggers

Una migración nueva y reversible reemplazaría **solo las definiciones necesarias**, sin eliminar triggers ni suspenderlos: `store_r01_order_guard` y `store_r01_attempt_guard` aceptarían únicamente las transiciones financieras de la función restringida, con verificación coherente, estados de origen permitidos y campos vinculados. Sus triggers de auditoría registrarían acciones y correlación financiera adecuadas; la auditoría de concesión ocurriría en la misma operación. `store_b02b_entitlement_guard` conservaría todas las comparaciones de orden/intento/archivo, 336 horas y límites, y exigiría además la verificación aplicada por la operación restringida. `store_b03c_evidence_guard` permitiría `APPLIED` y `processed_at` solo para el evento causal durante esa operación; identidad y huella seguirían inmutables. Las guardas B-03A y B-03B no necesitan relajación general. El orden de evaluación de triggers y la visibilidad de filas dentro de la transacción se probarán en PostgreSQL 16.

La migración registra definición previa y reversión explícita de cada función. Pruebas con usuarios web y financiero separados comprobarán que `save()`, `QuerySet.update()`, `bulk_update()`, Django Admin y `UPDATE`/`INSERT` SQL ordinarios siguen rechazados, incluso tras insertar una fila B-03C `VERIFIED`. También se prueba que funciones públicas, marcadores de sesión manipulables y roles miembros no abren acceso. No se usa el dueño de base ni superusuario para simular al usuario web.

## 7. Pruebas y puertas de aceptación de la futura implementación

Con proveedor determinista, cubrir evento de éxito válido, faltante, vencido, duplicado e incompatible; Session/PaymentIntent/líneas cruzados; monto, MXN, cuenta, entorno, precio, producto, cantidad, captura y archivo; eventos fuera de orden; reintento con y sin webhook; falla del almacenamiento antes de concesión; fallos inyectados en cada escritura de la transacción; respuesta perdida después de commit; dos trabajadores concurrentes; y webhook tardío. El resultado permitido es **cero confirmaciones parciales** y, ante éxito, una orden `PAID`, un intento `SUCCEEDED`, un derecho, auditoría y evento aplicado cuando corresponda.

Las pruebas PostgreSQL 16 deben usar conexiones y roles reales, comprobar migración y reversión en base desechable, conservar todos los triggers previos y demostrar rechazo de SQL ordinario. Ejecutar también suite completa, Django check, migraciones y diff. No se contacta Stripe real durante esta etapa. La activación TEST y LIVE exige aprobaciones y controles operativos separados.
